# UI audit -- the Electron app, 2026-09-16

READ-ONLY audit of `app/` (main.js, preload.js, bridgeHosts.js, renderer/{index.html,app.js,app.css,data.js})
against the running instance (electronmon, CDP 9223, one main process PID 46600, one `src/ff.ts serve`
helper PID 32580, two logged-in guests: `espnview` on fantasy.espn.com and `yahooview` on
football.fantasysports.yahoo.com). Nothing in this audit edited a file or wrote to ESPN/Yahoo.

Purpose: the evidence a UI redesign gets cut from, given the owner's framing -- "a lot of dead
code/old modules that aren't used, UI buttons don't work correctly, we probably don't need as many
buttons in the new paradigm where we are running it as a Claude Code agent CLI/MCP."

**Method, stated up front, because a verdict is only as good as how it was reached.** Every verdict
below is reached two ways and both are reported: (a) reading the chain control -> handler ->
`window.mc.*` -> preload channel -> `ipcMain.handle` -> engine verb, and (b) driving the real running
renderer over raw CDP (`Runtime.evaluate` with `Runtime.consoleAPICalled` / `Runtime.exceptionThrown`
/ `Log.entryAdded` capture) and reading the resulting DOM. Where (a) and (b) disagree, (b) wins.
Reachability is computed mechanically from a call map (scratchpad `callmap2.mjs`), not by eyeballing
-- the renderer has several functions that LOOK live because a registry object names them, and are
not, which is exactly the failure a hand-read misses.

---

## 0. Headline findings

1. **The two reworked features work.** League tabs and per-platform webviews behave correctly in
   both directions, including the P-4 case that used to drive the ESPN guest to a foreign league:
   switching to the Yahoo league left `espnview` parked on its own URL and navigated only
   `yahooview`. Verified live (section 3).
2. **About 40% of `app/renderer/app.js` is unreachable.** Five whole view functions
   (`views_team`, `views_room`, `views_copilot`, `views_live`, plus their 14 helpers) survive only
   because a `views = {...}` object names them; nothing indexes that object except
   `syncTeam()`'s `views.team()`, and `cur` can never hold `"team"`. That is ~350 lines, and with
   them the entire in-app Assistant chat and the entire draft control bar.
3. **Six preload channels are invoked by nobody**, and nine more are reachable only from the dead
   code above. The engine side of two of them (`data-sources`, `tools/push_sheet.py`) has no other
   consumer at all, so it is dead too.
4. **Three buttons/controls are genuinely broken, not merely unused** (section 2): the "Hide OUT"
   checkbox (its predicate names a field the board no longer serves), the **Owner** sort header
   (sorts on a row field that does not exist -- Owner is an overlay), and the Model page's three
   registry sections (the `model-page` RPC returns null in the running instance and the renderer
   returns silently, leaving three empty section headers).
5. **A background job is failing invisibly.** The in-app scheduler is ENABLED (every 15 min) and its
   last tick reported `FAIL scorecard --no-forward --no-odds -- RangeError: Missing named parameter
   "fk"`. The renderer never calls `scheduleGet`/`scheduleSet`/`tickNow`/`onSchedulerTick`, so the
   app has no surface on which that failure could ever appear.
6. **The left-rail Draft Cockpit is permanently in alarm.** It reads a 10.6-day-old
   `live-state.json` and renders `STALE 915215s -- Agent silent ... likely dead or out of the room.
   CHECK IT.` all season. A panel that cries wolf gets ignored -- which is precisely the failure its
   own source comment says it exists to prevent.
7. **The app's irreplaceable value is narrow and real**: the two logged-in `<webview>` guests plus
   the loopback bridge (`/fetch`, `/read`, `/read-frame`, `/click`, `/write-transaction`), which
   **12+ engine modules depend on**. Everything else in the UI has a CLI or MCP equivalent.
8. **One thing this audit could not settle, and should not:** the in-app Assistant is removed in code
   but retired by **no decision record**, while `README.md` and `docs/mcp.md` both still describe it
   as a live feature. That needs an owner call before its remains are cut (5.3).

## 5. The new-paradigm question

### 5.1 What the app is still uniquely needed for

1. **The two logged-in `<webview>` guests + the loopback app bridge.** This is the whole ballgame.
   `app/main.js`'s `startBridge()` publishes `data/app-bridge.json` (port + random token) and serves
   five routes -- `/fetch` (authenticated GET, per-platform allowlisted via `app/bridgeHosts.js`),
   `/read` (off-the-record real-Chromium render of any public page), `/read-frame` (nested
   cross-origin frames -- the only way to read Fantasy Chat), `/click` (hardened React-compatible
   clicker), `/write-transaction` (the one narrow write). The engine depends on it from **12+
   modules**: `src/browser/appBridge.ts`, `src/browser/webviewPage.ts`, `src/agent/browserTools.ts`,
   `src/data/eligibility.ts`, `src/data/leagueRosters.ts`, `src/data/leagueTransactions.ts`,
   `src/league/platform.ts`, `src/league/yahoo.ts`, `src/inseason/proposeTrade.ts`,
   `src/weekly/espnProjections.ts`, `src/ff.ts:4456`. **No CLI or MCP equivalent exists or can
   exist** -- the point is that the credentials live in a browser profile the user logged into by
   hand. CLAUDE.md's standing rule ("Browser access -- always the Electron app") rests on this.
2. **Being a stable CDP target.** `ff <draft verb> --app` and the MCP browser tools
   (`read_page`/`read_dom`/`click_page`/`fill_page`/`press`/`read_frame`/`navigate`/`scroll_page`/
   `wait_for`) drive the guest through `src/browser/webviewPage.ts`. The app must be running and the
   guest must be attached -- which is why the off-screen-hide trick (verified in 3.5) is
   load-bearing rather than cosmetic.
3. **The league switch that stamps the board.** `leagueSetActive` -> `league-set-active` clears and
   rebuilds the single-slot value board under the new league and reports what it did. There is a CLI
   verb behind it, but the app is where the switch is *visible*, and where the browser follows the
   league to the right platform in one click. Worth keeping as UI.
4. **The in-app scheduler.** `schedulerCycle()` runs `ff inseason-tick` every N minutes for as long
   as the window is open, with no OS Task Scheduler entry. Genuinely app-only -- and today
   completely invisible (3.7).
5. **A human eye on a live auction.** During a draft, the cockpit + the real draft room side by side
   is a thing a terminal cannot be. Eleven months a year it is dead weight; on draft day it is the
   product.

## Appendix -- method notes

- **Reachability was computed, not eyeballed.** `callmap2.mjs` strips comments, finds top-level
  declarations, and counts references excluding the declaration line; reachability was then walked
  from the real roots. The `views` object is the reason a hand-read would have called
  `views_room`/`views_copilot` live: they are named by a registry nothing indexes.
- **CSS was classified in two buckets, not one.** "No occurrence anywhere" and "occurs only inside a
  line range proven dead" are different findings with different risk, and four apparent no-occurrence
  hits (`dot-*`, and the DAG `kind` classes) were **corrected against the engine that emits them**
  rather than reported as dead. The remaining `.dag-node.config` survived that check.
- **knip's silence about `app/` is a config fact, not a finding** (4.1). Reporting "knip found no
  unused files" without that caveat would have been a measurement of the ignore list.
- **Every "no effect" verdict was checked against the data, not just the click.** "Hide OUT" changes
  nothing *and* the field it tests is absent from 529/529 rows; "Owner" does not reorder *and*
  `Owner` is the only declared column missing from the row. Conversely "Hide drafted" changes nothing
  and is reported as a **correct null**, because `TEAM` is legitimately empty -- a no-op click alone
  could not have told those two apart.
- **Not exercised, by instruction:** anything that writes to ESPN/Yahoo, bids, nominates, proposes a
  trade, submits a guest form, starts a refresh/materialize/ingest/train job, or raises a JS dialog.
  Those chains were verified by reading only, and are marked "chain intact" rather than WORKS.

### The two engine-side defects

**(a) The scheduler's scorecard routine.** WP2's `format_key` migration added `@fk` to every

(`src/weekly/scorecard.ts:696`) was the one missed -- two-of-three-callers-fixed, which looks done.

- BEFORE (this audit, 3.7): `FAIL scorecard --no-forward --no-odds 0.5s -- RangeError: Missing named parameter "fk" ... 2/3 steps ok in 59.3s`
- AFTER (live tick, read off the new Status page): `ok   scorecard --no-forward --no-odds     0.5s` ... `3/3 steps ok in 59.0s`, `{"ran":["actuals","scorecard","decisions"],...,"ok":true}` -- and the Status scorecard table now shows `stream | 1 week frozen | 12 models` (QB/QB_line ... DST/DST_line), the rows the broken insert could never write.
- Locked by `test/scorecard-stream-fk.test.ts`, which was written FIRST and reproduced the exact
  `RangeError` against a temp store before the fix. It also asserts the positive direction (rows
  land, each carrying a `format_key`), because a stream block that silently picked nobody would also
  stop throwing and read identically to a fixed one.

**(b) `/write-transaction`.** It was the last bridge route resolving its guest with

ESPN-only, as its url allowlist already is. NOT exercised live: it writes to a league.

### FIX 1, applied: errors stop being swallowed

`main.js`'s nine `.catch(() => null)` are one `rpcOr()` returning `{error}`, and every Status section
renders its error where its content would be. This is what turned a live engine fault into three
blank section headers for days (1.8). `boot()` distinguishes `{error}` from "0 players" too.
